# 文明火种（Civilization Spark）项目分析与修复报告

日期：2026-10-19

## 1. 项目定位

这是一个 C++23 的“分布式 LLM 文明模拟”原型，主要模块如下：

| 模块 | 作用 |
| --- | --- |
| `src/ai` | 共享 llama.cpp 模型、13 个智能体、批量解码调度 |
| `src/civilization` | 辩论、学习、淘汰、重生四阶段模拟 |
| `src/channel` | TCP、共享内存、RoCEv2（RDMA）、多通道封装 |
| `src/codec` | KFL-M v4 压缩帧（4 bit 会话号 + 索引 + CRC8） |
| `src/crc` | CRC8 与 CRC32C（可走 SSE4.2 硬件指令） |
| `src/quantum` | 量子启发式随机数、QKD 密钥生成 |
| `cuda` | 自定义 Transformer/Attention 内核（目前未接入 CPU 主流程） |

实际运行链路是：

1. `Simulation` 加载模型（可选）并创建 13 个 `LLMAgent`。
2. 有模型时走 `SharedModelPool` + `BatchScheduler`，多个 Agent 共享一个 llama 上下文、按序列批量解码。
3. 没有模型时走内置的 128 维、2 层 Transformer，作为纯 CPU 演示路径。
4. 辩论阶段用 KFL-M 帧交换通信统计。

## 2. 已修复的 Bug

### P0：llama.cpp 新版 API 导致主程序无法编译

`llama_tokenize`、`llama_token_to_piece`、`llama_token_eos` 在新版 llama.cpp 中接收的是
`const llama_vocab*`，原代码传的是 `llama_model*`。`civ_main` 在 Windows/MSVC 下直接编译失败。

修复：统一改为通过 `SharedModelPool::vocab()` 获取词表指针，并使用 `llama_vocab_eos` /
`llama_vocab_eot` 判断结束符。涉及 `src/ai/llm_agent.cpp`。

### P0：共享上下文的 `n_ctx` 被错误地按“每序列”设置

llama.cpp 中 `n_ctx` 是整个上下文池的总容量，实际每序列容量为
`n_ctx / n_seq_max`。原代码设置 `n_ctx=2048`、`n_seq_max=16`，导致每个 Agent 实际只有
约 128 个 token 的上下文，几轮对话后就无法继续解码。

修复：加载时把总容量设置为 `n_ctx_per_seq * MAX_SEQ`，同时保存每序列容量；
长提示词会截断到可用窗口内，必要时清空该序列 KV 后重新开始。涉及
`include/civ/ai/shared_model.hpp`、`src/ai/shared_model.cpp`、`src/ai/llm_agent.cpp`。

此外，每次提示词解码和批量生成前都会用 KV cache 的实际位置校正本地 `n_past`，
避免 EOS、滑动窗口重建或异常路径造成位置漂移，从而触发 llama.cpp 的
“Y = X + 1”位置连续性错误。

### P0：`QuantumRNG::next_range` 溢出，返回值越界

原实现把 64 位随机数直接乘以 32 位范围，乘积超过 64 位后截断，再取错误的中间位，
导致 `next_range(5, 9)` 可能返回 `196232176` 这类巨大值。

修复：先取 32 位随机数，再做 32 位 Lemire 无偏取模。新增 10000 次范围边界测试。
涉及 `src/quantum/quantum_rng.cpp`。

### P1：KFL-M 帧会话号未截断

会话号只有 4 bit，原代码在 `session >= 16` 时会污染类型位，导致编码和解码不一致。

修复：编码时执行 `session &= 0x0F`；CRC 失败时同时清零会话号、索引和命中标志。
涉及 `src/codec/frame_v4.cpp`。

### P1：Windows TCP socket 有效性判断错误

Windows 的 `SOCKET` 是无符号类型，`sock_ < 0` 永远为假，`socket/accept` 失败时不会抛异常。

修复：统一使用 `INVALID_SOCKET` 判断；构造失败时关闭已创建的 socket；增加 64 MiB
最大帧限制，防止对端长度字段导致无界内存分配；POSIX 发送使用 `MSG_NOSIGNAL`，
避免对端断开时触发 SIGPIPE。涉及 `src/channel/tcp_channel.cpp`。

### P1：共享内存通道的容量下溢与覆盖

原实现没有检查 `size_ <= sizeof(Header)`，`size_ - sizeof(Header)` 会下溢；
写端允许 `write_seq - read_seq > 1`，可能在读者读取前覆盖上一帧；Linux 客户端关闭时
还会 `shm_unlink` 掉服务端创建的共享内存对象。

修复：校验容量和帧长度；写端在存在未读帧时等待；只有创建者负责 `shm_unlink`；
Header 使用 placement new 正确初始化。涉及 `src/channel/shm_channel.cpp`。

### P1：CUDA Attention 内核缺少 softmax

原内核直接把注意力分数乘 V 后求和，没有归一化，结果不是注意力输出。

修复：加入数值稳定的两遍 softmax。涉及 `cuda/attention_kernel.cu`。
该内核目前尚未被主流程调用，因此只做了静态修复，未做 GPU 运行验证。

### P2：同一种子仍然不可复现

`main` 先把 `std::rand` 设为种子，紧接着又用 `time(nullptr)` 重新播种，导致相同种子
运行结果不同。修复为只使用传入种子。涉及 `apps/civilization_main.cpp`。

### P2：批解码超过 `n_batch` 时会断言/失败

长提示词的 token 数可能超过 `n_batch=256`。修复为按 `n_batch` 分块提交，并用
`llama_get_logits_ith` 按批次内位置取回 logits。涉及 `src/ai/shared_model.cpp`。

### P2：RDMA 资源与缓冲区问题

- 服务端监听 id 被连接 id 覆盖，导致监听资源泄漏；已拆分 `listen_id_`。
- 构造函数抛异常时不会进入析构函数，已增加清理路径。
- `cfg.buf_size` 未生效、未按 4096 对齐；已修复。
- CQ 轮询未区分发送/接收完成事件；已按 `wr_id` 过滤。
- 关闭时避免重复销毁同一个 `rdma_cm_id`。

说明：本机没有 RDMA 硬件，以上修改只通过代码审查，未做运行时验证。

### P2：构建与配置

- 新增 `CIV_ENABLE_CUDA` 选项，没有 GPU 时可显式 `-DCIV_ENABLE_CUDA=OFF`。
- MSVC 增加 `_CRT_SECURE_NO_WARNINGS`，消除 `getenv` 警告。
- Dockerfile 的模型路径从不存在 `tinyllama.gguf` 改为实际文件名。

## 5. 建议的下一步

### 纯 CPU 开发

```bash
cmake -S . -B build-cpu -DCIV_ENABLE_CUDA=OFF -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build-cpu --parallel
ctest --test-dir build-cpu --output-on-failure
unset CIV_LLAMA_MODEL
./build-cpu/civ_main 42
```

### 租赁 GPU 后

```bash
cmake -S . -B build-gpu -DCIV_ENABLE_CUDA=ON \
      -DCMAKE_CUDA_ARCHITECTURES=89 \
      -DCMAKE_BUILD_TYPE=Release
cmake --build build-gpu --parallel
export CIV_LLAMA_MODEL=/path/to/Spark-X2.5-4B-Q4_K_M.gguf
export CIV_N_CTX=512           # 6 GB 显存推荐；越大 KV 缓存越大
export CIV_N_GPU_LAYERS=99
./build-gpu/civ_main 42
```

`CMAKE_CUDA_ARCHITECTURES` 按租用显卡调整：A100 用 80，RTX 30 系用 86，
RTX 40 系用 89，H100 用 90。

注意：`CIV_N_CTX` 是每个 Agent 的上下文长度，实际分配的总 KV 容量为
`CIV_N_CTX * 16`。Spark 4B 在 2048/Agent 时 KV 缓存可能达到数 GB；
显存或内存紧张时可降到 `CIV_N_CTX=512` 或 `256`。
